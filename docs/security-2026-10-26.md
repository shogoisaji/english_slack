# セキュリティ対策と依存関係の確認（2026-10-26）

## 対策

- 未使用の `POST /word-list/random` とランダム取得処理を削除。URL 確認も含め `404` を返し、HTTP リクエストから Slack へ投稿できる経路を閉鎖。
- `GET /word-list` に Cloudflare の回数制限を追加。接続元 IP ごとに拠点あたり 60 回/60 秒を目安とし、拒否時は DB を読まずに `429` と `Retry-After: 60` を返す。回数制限自体が失敗した場合も DB への処理を進めない。
- CORS で許可するメソッドを `GET` のみに変更。投稿経路の閉鎖はサーバーのルート削除で実施しており、CORS のみに依存しない。
- Workers Logs とソースマップのアップロードを有効化。定期実行ごとの識別子、予定時刻、開始時刻、起動遅延、DB・Slack 処理の開始段階、送信完了、成功・失敗を記録。
- Slack 要求を 10 秒でタイムアウト。HTTP エラー・API エラーを失敗として扱い、送信関数では再送しない。
- `wrangler.jsonc` を Git の管理対象に追加。秘密情報は `.dev.vars` と Worker secret に保持。

Cloudflare の回数制限は拠点内での概算で、全世界共通の厳密な上限ではない。ログには保持期間がある。仕様は [Rate Limiting](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/) と [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/) を参照。

## 脆弱性監査

- 更新前：8 パッケージ（High 7、Low 1）。実行時依存の Hono・Drizzle と開発用依存を含む。これは監査対象パッケージ数で、個別のアドバイザリ数ではない。
- 更新後：`npm audit --include=dev` で 0 件。
- 更新後：`npm outdated --include=dev --json` は `{}`。

最新 Wrangler 4.152.0 が使う Miniflare は Undici 7.29.1 を固定している。この版には [過剰な Content-Encoding による DoS](https://github.com/nodejs/undici/security/advisories/GHSA-xjj6-f33q-929c) などの報告が残るため、`overrides.miniflare.undici` で同じ 7 系の修正版 7.30.1 に限定更新。Wrangler 更新時は、この上書きが引き続き必要か確認する。`npm audit fix --force` による Wrangler の旧版への変更は行っていない。

元の Drizzle には [SQL 識別子のエスケープに関する修正](https://github.com/drizzle-team/drizzle-orm/security/advisories/GHSA-gpj5-g38j-94v9) が未適用だった。現在のクエリは固定スキーマを使っており、監査結果だけから悪用や今回の遅延との因果関係は判断できない。

## 本番反映

バージョン `427b146a-15af-47b8-9e36-11a8e394da0f` をデプロイし、Cloudflare API で 100% の配信を確認。

- ログ保存が有効（`observability.enabled`、`logs.persist`、`logs.invocation_logs` が `true`）。
- `READ_RATE_LIMITER`、既存 DB、既存 Slack secret のバインディングを確認。
- Cron は `0 22,23,0-13 * * *` のまま。
- 本番の `GET /` は `200`、`GET /word-list` は `200` で 10 件返却。
- 本番の `GET /word-list/random` は `404`、同パスの CORS preflight の許可メソッドは `GET` のみ。

本番の疎通確認では `GET` と `OPTIONS` だけを使用し、手動投稿や cron の強制実行は行っていない。閉鎖 POST の動作は単体テストとローカルの実際の Workers 実行環境で検証した。

今回の対策は、過去の攻撃の有無や、13 時台の遅延原因を確定するものではない。今後の遅延は `scheduled_started.delayMs` と各処理段階の時刻・結果を照合して調査する。
